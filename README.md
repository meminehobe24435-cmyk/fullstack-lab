# fullstack-lab · 设备数据看板（前端 + 后端 + 数据库 + 缓存）

一个**完整的前后端小项目**，重点不是"能跑"，而是把三件常被含糊带过的事做成**可复现的证据**：

1. **索引优化**：同一查询，加索引前后对比 **查询计划（SCAN → SEARCH USING INDEX）** 与**平均耗时**；
2. **缓存收益**：自研 **LRU + TTL 缓存**，按热点分布压 1000 次请求，输出**命中率 / 查库次数 / 淘汰数**；
3. **前后端联调**：Vue 3（CDN，无构建）+ Python 标准库 REST API，用 **Chrome 无头渲染抓 DOM** 断言页面上真的渲染出了后端的设备序列号。

## 1. 技术栈与运行

| 层 | 实现 | 说明 |
|---|---|---|
| 后端 | **Python 3.8 标准库**（`http.server` + `json`） | 零第三方依赖，`python -m app.server` 直接起 |
| 数据库 | **SQLite**（`sqlite3`） | 表结构 + 造数据（固定随机种子，可复现）+ 索引 |
| 缓存 | **自研 LRU + TTL**（`app/cache.py`） | 命中/未命中/淘汰/过期全计数 |
| 前端 | **Vue 3 + HTML/CSS/JS（ES6+）** | 通过 CDN 引入，无构建步骤；分页/筛选/排序/统计卡片 |
| 测试 | **unittest**（标准库） | 缓存语义、SQL 与索引、REST 接口、静态页 |

```bash
make seed        # 生成数据（400 台设备 / 10000 条读数）
make test        # 全部自检（含索引前后计划与耗时断言）
make bench       # 索引优化与缓存收益的实测数字
make verify-ui   # 起服务 → Chrome 无头渲染 → 抓 DOM 断言 + 截图
make serve       # 手动起服务，浏览器打开 http://127.0.0.1:8000/
```

## 2. 接口

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/health` | 健康检查 |
| GET | `/api/devices?page=1&size=20&status=fault&line=A1&order_by=temperature&desc=1` | **分页 + 筛选 + 排序**；`order_by` 走白名单，不拼接注入 |
| GET | `/api/devices/<id>` | 设备详情（不存在 → 404） |
| GET | `/api/devices/<id>/readings?limit=10` | 最近 N 条读数（最吃索引的查询） |
| GET | `/api/stats` | 统计（总数 / 按状态 / 平均与最高温度 / 故障占比） |
| GET | `/api/cache/stats` | 缓存命中率、淘汰数、实际查库次数 |

非法参数返回 **400**，不存在返回 **404**，内部异常返回 **500**（并有兜底，服务不会崩）。

## 3. 实测数据（本机输出，可复现）

`make bench` 会打印下面这几组数字（每次跑略有波动，趋势一致）：

- **索引**：`SCAN readings` → `SEARCH readings USING INDEX idx_readings_device_ts`，平均耗时从 **约 2 ms 降到约 0.02 ms**；
- **缓存**：1000 次请求（20% 热点 + 80% 随机），**命中率约 80%**，实际查库次数从 1000 降到约 200，淘汰次数与容量一致；
- **前端**：无头渲染后 DOM 中能找到真实序列号（`SNxxxxxx`）、统计卡片与缓存命中率，并保存整页截图 `docs/dashboard.png`。

## 4. 设计决策（面试常问）

1. **为什么 `order_by` 用白名单？** 排序列不能参数化绑定（`ORDER BY ?` 无效），只能拼字符串——**所以必须白名单**，否则就是注入点。
2. **为什么缓存键要包含全部查询参数？** 分页/筛选/排序任一不同就是不同结果；漏掉一个参数会让不同请求互相污染。
3. **LRU 为什么用 `OrderedDict` + `move_to_end`？** 命中即刷新为最近使用；淘汰取 `popitem(last=False)`，O(1) 完成，不用自己维护双向链表。
4. **TTL 过期为什么放在 `get` 里判断？** 惰性删除省掉后台线程；代价是过期项会占位到被访问或淘汰，所以同时保留 LRU 容量约束。
5. **索引为什么建在 `(device_id, ts DESC)`？** 查询是"按设备取最近 N 条"，复合索引让**过滤 + 排序**一次走完，避免临时排序（B-tree 顺序即结果顺序）。
6. **为什么要统计"实际查库次数"？** 只报命中率会被"缓存了但没省事"糊弄过去；查库次数下降才是真实收益。

## 5. 局限（如实说明）

- 数据库用 **SQLite**，**没有用 MySQL / PostgreSQL 真服务**；索引结论在 SQLite 上实测，不同数据库的执行计划与优化器行为会有差异。
- 缓存是**进程内自研实现**，**不是 Redis**：没有持久化、没有分布式一致性、没有淘汰策略插件。
- 前端用 **Vue 3 CDN**，**没有 React**，也没有构建工具链（Vite/Webpack）、路由、状态管理。
- 未做鉴权、并发压测、容器化部署与 CI。
